# SheOnTheRun — Admin Panel: Build Plan

**Goal.** Give Fatima a private, easy admin panel where she manages everything on the site that changes, and nothing else. She edits in the panel and the live site updates. She never touches code, files or GitHub.

**Not in scope.** The design, layout and page structure of the public site. They stay as they are.

**Status (4 Oct 2026): phases 0–4 are built (awaiting merge and deploy).** Phase 4 adds the dashboard, activity log, nightly backup, draft preview, the meal-plan library and the owner how-to ([how-to-for-fatima.md](how-to-for-fatima.md)). Phase 5 (card payments) waits for a merchant account.

**Earlier status (1 Oct 2026):** Phase 0 code is built and tested locally (sign-in, 2-step code, recovery codes, hosting check, deploy workflow). Waiting on the hosting steps in [hostinger-setup.md](hostinger-setup.md).

## 2. Architecture

### Recommendation: run it on the Hostinger Cloud Startup plan she already has

```
 Visitors ──► Static site in public_html (HTML/CSS/JS, as today)
                │  loads /data/*.js  ◄── regenerated by the backend on Publish
                ▼
 Fatima ───► sheontherun.com/admin (private) ──► PHP API ──► MySQL database  (content, orders, messages, audit log)
                                                    │          Uploads folder  (photos)
                                                    └────────► Email via Hostinger SMTP (order + message alerts)
```

| Layer | Choice | Why |
|---|---|---|
| **Hosting** | Hostinger Cloud Startup (already owned) | `sheontherun.com` is already attached. No DNS or nameserver changes, no new vendor, no extra cost. |
| **API** | PHP 8.x, small framework-free codebase | Runs natively on the plan. Nothing to install or keep alive. |
| **Database** | MySQL (hPanel) | Orders, messages and content are structured data. |
| **Files** | Uploads folder on the same hosting | Photos plus generated content files. |
| **Login** | Email + strong password (argon2id), **2-step code (authenticator app)**, login rate-limiting | Built by us, so it must be done carefully. See section 4. |
| **Admin UI** | Single-page app at `/admin`, mobile-first | She will edit from her phone. Styled with the brand (lilac/teal). |
| **Email alerts** | Hostinger email (SMTP) | "New order" and "New message" arrive in her inbox. |
| **Backups** | Hostinger's automatic backups plus a nightly cron export of the database | Two independent copies. |

**Cost:** nothing beyond what she already pays. **To verify in hPanel before we start:** PHP 8.1+, MySQL, SSH or Git deploy, cron jobs, SMTP email, and enough disk space for photos (the site has about 480 image files).

### The key design choice: the public site doesn't change

The site is already driven by `window.SITE_SHOP`, `window.SITE_RUNS`, `window.SITE_OFFER` and the other `data/*.js` files. So **Publish regenerates the same files from the database** and writes them to the same paths:

- `site.js`, `motion.js` and the HTML pages are barely touched, and the Arabic pages keep working.
- Visitors get plain static files, so the public site stays fast and doesn't depend on the database being up.
- **Draft vs live.** She edits freely, then presses **Publish**. Nothing she half-types goes live.
- **Rollback.** Each publish is a snapshot. "Restore previous version" is one tap.
- **Journal articles** are generated as real HTML pages by the backend (good for Google), along with `feed.xml` and `sitemap.xml`. This replaces the GitHub Action for those, so publishing is instant.

### Deploying code vs. her content
Code (HTML, CSS, JS, PHP) is deployed from GitHub to Hostinger by Git deploy or an Action over SFTP. The generated files (`data/*.js`, `journal/`, `uploads/`) belong to the admin panel, so **the deploy excludes them** and never overwrites her work. The repo keeps its current `data/*.js` as the seed and fallback.

### Alternatives considered

| Option | Verdict |
|---|---|
| **Cloudflare Workers + D1** (earlier proposal) | Free and robust, but adds a new vendor and a nameserver change when she already has hosting. A good fallback. |
| **Git-based CMS (Sveltia/Decap)** | Simplest, but she needs a GitHub account and there's **no orders dashboard**. |
| **Shopify for the shop** | Monthly cost and duplicated design, and it leaves runs/services/journal unmanaged. |
| **WordPress + WooCommerce** | Would mean rebuilding the site she already has. Not recommended. |

## 3. Orders and payments

**Launch (phase 3):**
- Checkout posts to the PHP API instead of Formspree or WhatsApp.
- **The server recalculates prices** from the database, because the browser is never trusted for amounts.
- The order is stored, she gets an email alert, and the customer sees the "Order received" screen (as now).
- Payment options: **cash on delivery** plus **Whish/OMT transfer** (the customer sends payment and gives a reference). She marks the order *Paid* by hand.
- Spam protection: a hidden honeypot field, rate limiting, and optionally Cloudflare Turnstile (free, works without moving DNS).
- Stock: optional "quantity left"; at 0 the product turns **sold out** automatically.

**Later (phase 5), once she has a merchant account:**
- Card payments through a Lebanese gateway (e.g. Areeba, Whish Pay), or Stripe if she or a partner has a company abroad.
- The PHP API creates the payment session and receives the confirmation webhook. The order flips to *Paid* on its own.
- No change to the admin panel structure: orders already have a payment status.

## 4. Security and safety

- **Access.** `/admin` and `/api/admin/*` need login: hashed passwords (argon2id), authenticator-app 2-step code, secure session cookies, CSRF protection, lock-out after repeated failures. Optionally an IP allow-list or a second password on the `/admin` folder.
- **Secrets** (database password, API keys) live in a config file outside the public folder, never in the repo or browser. All database queries are parameterised.
- **Input handling.** All content is validated on the server. Rich text is sanitised. Uploads are limited to image types and size.
- **Personal data.** Orders contain names, phones and addresses. Only admins can read them, and she can delete or export an order. The privacy note on the site will say what's collected.
- **Audit log.** "Who changed what, when", visible in the panel.
- **Backups.** Hostinger's automatic backups, plus a **nightly cron export** of orders and content to a private location.
- **Mistake protection.** Deleting asks for confirmation. Publish history allows rollback.

## 5. How the panel should feel

- **Mobile-first.** A bottom tab bar on phone: *Orders · Shop · Events · More*. A sidebar on desktop.
- **Dashboard.** New orders, upcoming events with places left, unread messages, "Arabic missing" count, last published time.
- **Plain language.** "Sold out" toggles, a date-time picker, drag to reorder. No JSON or field names.
- **Forms with guard-rails.** Price must be a number, sizes are chips, event end can't be before the start, required fields are marked.
- **Photo upload.** Pick a photo and it is resized automatically into the four widths and two formats the site uses today, with a prompt for alt text.
- **Preview.** "Preview changes" opens the real site with the unpublished draft before she presses Publish.
- **Bilingual.** English | العربية side by side, and the admin itself in English (Arabic UI is optional later).

## 7. Testing and acceptance

- **Automated:** schema and validation tests, the publish generator produces files identical in shape to today's (diffed against the current ones), price recalculation tests, access-control tests (no login means no data), login lock-out and CSRF tests.
- **Manual on real devices:** the full flow on a phone (iOS Safari, Android Chrome) in English and Arabic (RTL).
- **Resilience:** disable the admin and API and confirm the public site still renders from the generated static files.
- **Her acceptance checklist:** add a product with photo · mark it sold out · add an event with 8 places · cancel an event · edit a package price · publish an article · confirm an order · roll back a publish.

## 8. Risks

| Risk | Mitigation |
|---|---|
| Card gateway approval is slow or unavailable | Launch on cash on delivery plus Whish/OMT. The panel is already built for payment status. |
| Custom-built login is a security-sensitive part | Standard, well-tested practices (section 4), 2-step code, rate limiting, and a security review before launch. |
| She breaks something by publishing a mistake | Draft/Publish separation, validation, one-tap rollback. |
| Shared-hosting limits (disk, PHP memory, resource caps) | Photos are resized on upload, and we check the plan's limits in phase 0. |
| Arabic text quality | Both languages are editable by her or a native reader, and the "Arabic missing" badge keeps gaps visible. |
| Orders contain personal data | Admin-only access, minimal fields, deletion/export, a privacy note. |

## 9. Decisions needed before we start

1. **Hostinger access:** confirm PHP 8.1+, MySQL, Git/SSH and cron are available on the plan. (Domain is `sheontherun.com`.)
2. **Where her business stands for payments:** registered company? which bank? any account abroad? (This decides phase 5.)
3. **Who needs admin access:** just her, or you and the owner too? (All by email.)
4. **Journal:** does she want to write articles in the panel, or will you keep adding them yourself?
5. **Stock tracking:** simple "sold out" switch, or an actual quantity per size?
6. **Notification channel:** email only, or also a WhatsApp/phone alert for new orders? (Email is built in; WhatsApp alerts would need a paid API.)
7. **Admin language:** English only, or also Arabic?
